

## ADR-320 — S15e.3b: Windows PE32+ DLLs built by the production compiler

| Field | Record |
|---|---|
| Decision | **The request.** `build_request` takes a `WINDOWS_DLL` request on the `x86_64-windows-pe-v1` profile (architecture 1) instead of declining it: `B_DLL` (control word 46) is set and `B_ENTRY` names the request, so the driver's main function, unchanged, gives the general x86-64 program the request where it gives an entry. A DLL request on another target stays `build`'s (`WINDOWS-DLL-TARGET`, declined). The provenance names `x86_64-windows-pe-dll-v1`'s container lowering identity.<br>**The plan** (`xax_selfhost_general_dll.dll_plan`, when the PE profile's entry is a BUILD object): the request's package and build entry; the package's modules in order and each module's references in order, every reference-free TARGET decoded as `_build_windows_dll` does: an export (`WINDOWS-EXPORT-CARRIER`/`-IDENTITY` trailing bytes, `WINDOWS-EXPORT-NAME`), a forward (`WINDOWS-FORWARD-IDENTITY`, the `module.Symbol` pattern checked byte by byte), a DllMain (`WINDOWS-DLLMAIN-IDENTITY`); the exports sorted by name then CID, the forwards by name then target; `WINDOWS-DLL-ENTRY-EXPORTED`, `WINDOWS-DLLMAIN-UNIQUE`; `_check_dllmain` (`WINDOWS-DLLMAIN-SIGNATURE`; the call closure from a stack, `WINDOWS-DLLMAIN-LOADER-LOCK` for an indirect call or a foreign call outside `kernel32.dll`'s allowlist, quoting `library!name`).<br>**The closure.** After the entry's, each further root (the exports' functions, then DllMain) is checked (`NATIVE-ENTRY-FUNCTION`) and its new functions are visited and sorted by CID (`dll_sort`), as `extra_roots` appends them.<br>**The container.** `emit_pe_dll`'s checks after code generation (`PE-EXPORT-UNIQUE`, `PE-EXPORT-DLL-NAME`), then the PE writer with a DLL's headers (characteristics, subsystem, DLL image base, DllMain or no entry point) and `.edata` after `.idata` (`dll_edata`: the directory, address, name and ordinal tables, the DLL name and each name, a forward's target after its name).<br>**Python.** `_build_windows_dll` asks the XAX program first (`xax_pe.compile_pe_dll`), the bootstrap where it declines; `compile_pe_executable` keeps a BUILD entry on the bootstrap. |
| Rationale | DLLs were the PE profile's remaining `build` path; the plan's inputs are all in the store, and the container differs from the executable's only in its headers and export section. |
| Evidence | EXECUTED on Linux x86-64. Differential (bootstrap `_build_windows_dll` vs the XAX program, byte for byte or the same diagnostic, no decline): the `test_xax_pe_dll` DLLs (exports, a forward and DllMain, the DXGI COM DLL, the loader-lock and signature rejections) and 620 random DLL requests (`tests/dll_corpus.py`: 1-8 exports, forwards, DllMain variants, malformed carriers, two DllMains, duplicate names, a non-function export, a NUL in the package name, members split over modules): 294 DLLs and every rejection rule above. The driver builds them to `build`'s bytes and provenance (`test_xax_selfhost_general_build.py::test_windows_dlls`). |
| Limits | The hosted legacy register path on Windows still declines (ADR-317). A carrier the bootstrap fails to decode with a truncation, and an export of a CID the store does not hold, decline. |

## ADR-321 — S15e.7: accelerator deployments and SPIR-V modules built by the production compiler

| Field | Record |
|---|---|
| Decision | **Accelerator deployments (S15e.7a).** `build_request` takes architecture 4 with image format 3 (`PATH_ACCELERATOR` = 4; the requested artifacts checked before lowering against `ACCELERATOR_DEPLOYMENT`, `BUILD-ARTIFACT-SUPPORTED` otherwise); the general program's front end hands such a target to `xax_selfhost_general_accel.accelerator`: `compile_accelerator`'s checks in its order (`ACCELERATOR-TARGET-PROFILE`, `-SINGLE-BLOCK`, `-RETURN`, `-HOST-INTERFACE`, `-TARGET-OPS-ONLY`, `-DEPLOY-SEQUENCE`) and the packet, written as the image record's container bytes; provenance `ACCELERATOR_LOWERING_IDENTITY_V1`. A contract with a runtime dependency declines.<br>**SPIR-V modules (S15e.7b).** `spirv-vulkan-compute-v1` is a hosted profile (`PATH_SPIRV` = 5); the front end hands it to `xax_selfhost_general_spirv.spirv`: the entry contract (`SPIRV-KERNEL-ENTRY-CONTRACT`, its details formatted), the target's lists (`SPIRV-OP-TARGET-SUPPORTED`, `-TERMINATOR-`), `_Lowering`'s value classes (`SPIRV-VALUE`), static pointers (`pointer()` as an explicit stack machine: memo, the open-cycle None, the distinct incoming pairs sorted for `SPIRV-POINTER-STATIC`, `-ALIGNED`), the race rule (`SPIRV-KERNEL-OWN-ELEMENT`), `SPIRV-ACCESS-WIDTH`, then the module: every result id in the bootstrap's order (types, constants on first use, variables, labels, each case body, trap cases and their labels, the dispatch loop), sections in order. A trap terminator declines (its payload's reason is not in the program's stream).<br>**Python.** `build` asks the XAX program first for both (`accelerator_artifact`, `spirv_module`), the bootstrap where it declines. |
| Rationale | Both are small, self-contained backends of the bootstrap; S15e.7 needed only the general program's object table, so they join it rather than adding programs (the driver's main function is at the seed's capacity). |
| Evidence | EXECUTED on Linux x86-64. Differential: 120 accelerator requests (`tests/accel_corpus.py`: both M13 target packages, extra parameters, two blocks, a trap, a plain node, repeated or missing synchronization, another artifact) and 420 SPIR-V kernels (`tests/spirv_corpus.py`: the benchmark kernels with random sizes, random kernels over every lowered operation with narrow widths, divisions, loops carrying the bindings, and the entry-contract, value, race and target-list rejections), all byte for byte or the same diagnostic, none declined; the three ADR-124 benchmark modules are identical. The driver builds both to `build`'s bytes and provenance (`test_accelerator_deployments`, `test_spirv_modules`). |
| Limits | `SPIRV-POINTER-STATIC`, `-ALIGNED` and `-ACCESS-WIDTH` are written but not reached by any store the verifier accepts here. Trap terminators in kernels decline. |
