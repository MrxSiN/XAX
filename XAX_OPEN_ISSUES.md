# XAX Open Issues

Only issues requiring implementation, target, ecosystem, or benchmark evidence are listed here. None permits weakening `XAX_SPEC.md` invariants.

## OI-01 — AI token vocabulary, fallback framing, and handle namespace

**Question.** Which dedicated model tokens, fallback packet encoding, and local-handle namespace minimize total model tokens per successful semantic change without increasing invalid mutations or repair rounds?

**Fixed constraints.** Transport is versioned, deterministic, unambiguous, non-source, and measured with the actual tokenizer/model. Full persistent hashes need not appear in normal AI context.

**Evidence that closes it.** Controlled comparison of typed versus unified handles and multiple fallback framings across program creation, literal/op/control edits, type/resource/effect repair, stale-root recovery, and optimization tasks. Record tokens, error rates, repair turns, semantic entities, protocol bytes, and completion rates. Tokenizer-native vocabulary requires actual tokenizer/model integration.

**Earlier evidence.** One fixed 2026-09-29 static edit case measured generation-scoped `R0.0` against full-root text with `cl100k_base` and `o200k_base`; the alias reduced candidate output tokens from 60/61 to 28/28 and bootstrap transaction accounting from 77 to 47 bytes. The alias is implemented with ABA-safe generation freshness checks. The workspace now also has an exact serialized response-byte cap with deterministic positive-progress pagination, but the measured 178-byte cap increased the three-node query total from 424 to 520 bytes across pages; this is transport accounting, not tokenizer evidence. This evidence predates the 2026-10-01 model trial below and does not by itself select a transport.

**Transport-candidate evidence (2026-10-01).** `compiler/benchmarks/ai_native` now compares two handle namespaces (current typed `P0`/`N0`; unified dense integers with kind out-of-band, `P0`→`0`, `Nk`→`k+1`) across three versioned `X1` fallback framings (`line` long verbs, `pipe` short verbs with `|`/`;`, compact `json`). Strict decoders reject unknown versions/verbs/fields, cross-namespace handles, non-canonical integers, and JSON type confusion; all six candidates decode to one identical workspace transaction and reach the target root for all five reference edits. Raw views/packets and counts are in `transport-oi01.json` (offline `tiktoken` 0.14.0). Five-task view+packet totals, `cl100k_base`/`o200k_base`: typed line 191+71/186+71, typed pipe 191+68/186+73, typed json 191+88/186+88, unified line 176+71/171+71, unified pipe 176+61/171+66, unified json 176+81/171+81; view+packet bytes 484/434/500/438/388/440. Unified handles save 15 view tokens under both encodings; `json` costs the most packet tokens. Each candidate is also runnable as a model-trial arm (`XAX-<TYPED|UNIFIED>-<LINE|PIPE|JSON>`).

**Model-trial evidence (2026-10-01).** All 30 candidate trials (5 tasks × 6 arms, n=1 per cell) ran as fresh Claude Code `general-purpose` subagents on `claude-opus-5-5`; raw packets, per-invocation traces, and rows are in `runs-claude/` and `results-claude.csv`. Completion was 30/30. Harness-reported subagent tokens per arm (five tasks): typed line 278,750, typed pipe 280,478, typed json 280,648, unified line 278,301, unified pipe 281,968 (includes the standalone probe run), unified json 280,587; ~55.6k per trial is fixed harness context, so arm differences (about 1.3% peak-to-peak) are within run-to-run noise. Failed `verify`/`test` checks: line 0 (0/10 trials), pipe 2 (2/10; both submitted the unedited header-only packet), json 14 (9/10 trials; the model wrote the header and mutations as separate or nested arrays instead of one flat array). By handle namespace: typed 9, unified 7 failed checks, all attributable to framing. On this corpus and model, `line` framing is the only zero-repair candidate, `json` as specified is error-prone, and typed versus unified handles shows no measurable token or reliability difference.

**Remaining to close.** (1) Repeated trials (n>1) and a second model family; the measured token differences are below noise and the OpenAI/Codex arm has not run. (2) Task families absent from the corpus: program creation, control-flow edits, type/resource/effect repair, stale-root recovery (only the rejection path is tested), and optimization. (3) Tokenizer-native vocabulary requires real tokenizer/model integration and remains unavailable.

**Corpus/checker extension evidence (2026-10-02).** `compiler/benchmarks/ai_native` now adds exactly the six missing families without adding a seventh transport: program construction from a minimal semantic scaffold via the existing insertion mutation, branch-edge argument replacement via existing disconnect/connect mutations, verifier-driven `u8`/`u16` type repair, linear resource/effect repair, stale-root refresh/retry that advances from `R0.0` to `R0.1` before the requested edit, and one dead-node optimization request. All 11 tasks run through the same typed/unified × line/pipe/json `X1` arms. `corpus-oi01.json` contains 66 deterministic task/arm rows with the minimum local view, prefilled packet, exact target packet, semantic-entity count, byte counts, and exact final target root; every target packet decodes to the same transaction across framings/namespaces and reaches that root. The type/resource/stale prefilled candidates reject for the intended semantic reason and then pass after the exact repair. Trial recording now supports repeated `trial` rows and records client token usage, turns, failed checks, repairs, view/packet bytes, semantic entities, and final root; `oi01-summary` groups results by family and arm.

**Remaining after this extension.** No new OpenAI/Codex-family model trial was available in the implementation environment, so there is still no n>=3 model evidence on the expanded corpus and no second-family confirmation. No fallback framing or typed-vs-unified default is selected by this change. Tokenizer-native vocabulary still requires actual tokenizer/model vocabulary integration and remains the dedicated-vocabulary blocker; offline tokenizer counts are not substituted for model usage. OI-01 remains open.

## OI-02 — Canonical object and graph-fragment granularity

**Status: CLOSED (2026-10-02).**

**Question.** What objectization policy best balances edit locality, CID churn, deduplication, index/hash overhead, cache reuse, verification locality, and merge conflict size?

**Fixed constraints.** Each chosen object has one canonical encoding; unchanged objects retain CIDs; fragment boundaries do not alter runtime semantics.

**Evidence.** `compiler/benchmarks/bench_oi02_granularity.py` now compares the canonical function grain, the existing measurement-only `call_indirect` and block candidates, module packing, and one combined **stable-interface+block** candidate. The combined arm reuses the existing canonical kind-11 `CallContract` as the separately content-addressed immutable interface/control summary; a measurement-only stable declaration references that summary and a module binding references a separately objectized block-skeleton body. The summary therefore has no independently mutable duplicate signature/effect/resource/control copy. Reassembly derives the expected summary from the exact block body and type interface, rejects stale summary/body pairs, recursively resolves stable declarations, and must reproduce the exact canonical graph/function CIDs before verification or execution. Existing function/call-indirect/block deterministic bytes and CIDs remain unchanged.

The corpus now includes `service-6x8-b4`, a generated six-module, eight-function-per-module, four-block service-like DAG with both intra-module and inter-module calls, in addition to the chain/star stress fixtures. Deterministic evidence is in `compiler/benchmarks/oi02_granularity_evidence.json`; raw fixed-count timing observations (5 samples/cell) are in `compiler/benchmarks/oi02_granularity_timing.json`. Focused tests include corruption and stale-summary negatives and pass 12/12.

On the service corpus, function grain is 28,713 B/154 objects and reads function `(0,0)` in 324 B. Stable-interface+block is 44,304 B/290 objects and reads the same function in 821 B. A first-leaf body edit that preserves the exact `CallContract` rewrites 104 function-grain objects/19,237 B with a 104-object verification frontier, versus 6 objects/1,255 B and a 5-object frontier for stable-interface+block. A shallower sibling edit is 30 objects/6,061 B and frontier 30 at function grain versus 6/1,255 B and frontier 5. By contrast an already-local entry edit is smaller at function grain: 5 objects/976 B versus 6/1,255 B, with the same 5-object verification frontier. Same-module merge overlap falls from 28 objects/5,745 B at function grain to 1 object/567 B for the stable candidate.

The synthetic stress fixtures show the same boundary. On `chain-8x16-b4`, a deep leaf edit falls from 266 objects/50,581 B and frontier 266 at function grain to 6/1,849 B and frontier 5; on `star-8x16-b4`, the leaf edit falls from 35/6,628 B and frontier 35 to 6/1,849 B and frontier 5. But the stable candidate pays persistent overhead: stores are 36.1% to 61.2% larger than function grain on the measured four-block workloads, function query bytes are 2.53x larger (821 B versus 324 B), and Python-bootstrap encode/decode/query timings are correspondingly slower. `call_indirect` retains similarly small rewrite sets but does not provide the same proof reuse because body-dependent verification still follows rebound callees.

**Decision.** Canonical **function grain remains the store-v1 default**. No finer candidate dominates it. Stable-interface+block fragmentation is bounded to derived/tooling use for body-only edits whose exact immutable `CallContract` summary CID is unchanged and whose measured/predicted function-grain dependency frontier would otherwise propagate through callers; an implementation should select it only when the local cost estimate shows lower rewrite bytes **and** a smaller verification frontier than function grain. For already-local edits, interface-changing edits, single-block bodies without demonstrated reuse, or query/store-size-sensitive paths, keep function grain. This policy preserves one semantic identity: fragmented units are reassembled and checked against the canonical function/graph CIDs, and store v1 is unchanged.

Model-visible token counts remain unavailable in this environment because no tokenizer/model trial is available; the benchmark records exact binary query/rewrite bytes and does not substitute them for model tokens. That unavailability is not a closure blocker under the OI-02 contract, which requires tokenizer/model tokens only if available.

## OI-03 — Recursion-group compact encoding

**Question.** Should non-recursive functions always use the direct `function` carrier, and what compact representation should trivial or singleton recursive groups use?

**Fixed constraints.** Recursive CID computation remains acyclic; recursive member identity is deterministic.

**Evidence that closes it.** Serializer/storage/token measurements over workloads with no recursion, self-recursion, and mutually recursive SCCs.

**Status: CLOSED (2026-10-01).** `compiler/benchmarks/bench_oi03_recursion.py` measures eight identical `x * k + c` bodies in three workloads with two carriers each; deterministic results are in `oi03_recursion_evidence.json` (reproduced by `tests/test_oi03_recursion.py`). Legal arms are whole-store verified and every entity executes to its reference value; measurement-only arms (including the one-member group around a non-recursive function, which the verifier now rejects) are never verified. Token counts are offline tiktoken 0.14.0 (`o200k_base`) counts of hex carrier envelopes and entity handles; no model was run.

| Workload / carrier | Carrier objects | Carrier bytes | Store bytes | Handle tokens | Carrier-hex tokens |
|---|---:|---:|---:|---:|---:|
| none / direct `function` | 8 | 856 | 4,682 | 306 | 954 |
| none / singleton `recursion_group` | 8 | 864 | 4,690 | 311 | 947 |
| self / `recursion_group` (current) | 8 | 1,128 | 5,911 | 302 | 1,228 |
| self / compact singleton (count omitted; measurement-only) | 8 | 1,120 | 5,903 | 306 | 1,249 |
| mutual rings 2+2+4 / `recursion_group` (canonical order) | 3 | 613 | 5,050 | 315 | 671 |
| mutual / one `function` per member (illegal CID-cycle comparator) | 8 | 1,120 | 5,902 | 298 | 1,243 |

Decision. (1) Non-recursive functions always use the direct `function` carrier: a one-member group costs exactly one body byte (the member count) and a `#0` handle suffix, yields a second CID for the same semantics, and cannot be a `call.direct` target (`XAX.STRUCT.CALL_TARGET`), so it has no benefit. (2) Self-recursive singletons keep the existing `recursion_group` carrier: the only possible compaction is the one-byte member count (8 B / 0.14% of store); carrier-hex token differences are CID-hash noise. No dedicated singleton encoding or new kind is warranted. (3) Mutually recursive SCCs keep `recursion_group`: sharing one reference table makes the group 45% smaller in carrier bytes and 14.4% smaller in store bytes than per-member objects; the cost is that an edit to one member changes the identities of all SCC members (2 or 4 here) but no member outside the SCC, while rewritten bytes stay at or below per-member (753–829 B versus 879 B). CID computation remains acyclic and member identity remains `(group CID, member_index)`. Enforced (2026-10-01): `XAX_SPEC.md` §3.3 now says MUST. The verifier rejects a group that is not exactly one recursive SCC (`XAX.STRUCT.RECURSION_SCC` / `GRAPH-RECURSION-SCC`, which covers non-recursive singletons and groups of separate SCCs) and a group not in canonical member order (`XAX.CANON.RECURSION_ORDER` / `GRAPH-RECURSION-ORDER`). The canonical order is the breadth-first order from the start member that gives the smallest per-member descriptor (erased key, renumbered callees). This is O(k²) in SCC size, and `canonical_recursion_order` exposes it to producers. `tests/test_oi03_recursion.py` checks that all four rotations of a 4-member ring canonicalize to one group CID and that 3 of the 4 raw rotations are rejected.

## OI-04 — Float format catalog and compact type vocabulary

**Question.** Which floating formats and high-frequency type forms receive dedicated pre-interned/transport IDs rather than structural descriptors?

**Fixed constraints.** Exact float semantics and canonical type identity are preserved.

**Evidence that closes it.** Serializer size, compiler complexity, AI token usage, and mutation reliability across representative numeric/target workloads.

**Prototype evidence (2026-10-01).** `compiler/benchmarks/bench_oi04_type_vocabulary.py` compares the canonical structural encoding against two measurement-only compression families. The catalog-alias arms write references to catalog types as small indices instead of 32-byte CIDs, omit those catalog type objects, and add a 32-byte catalog digest to the header. The new `cid_dictionary` comparator is catalog-free: every CID referenced by at least two semantic objects is entered once in a deterministic store-wide dictionary carried by the container; references use small dictionary indices while one-use CIDs remain explicit. Both decoders rebuild each object's exact structural reference set, re-derive every CID, and rebuild byte-identical canonical store bytes. The dictionary decoder additionally requires the dictionary to equal the exact repeated-reference set, validates record/index/digest integrity, and rejects unknown indices, dual explicit/index encoding, and wrong expansions. Deterministic results are in `oi04_type_vocabulary_evidence.json`; tokens remain the previously measured offline tiktoken 0.14.0 counts and no model was run. Catalogs: `bits5` = `bits<1,8,16,32,64>`; `+float2` = binary32/binary64; `+float4` adds binary16/bfloat16; `common` adds memory effect, stack owner, and the seven opaque kinds. Floats use a measurement-only descriptor (form 6: radix, precision, emax, emin, encoding width, flags for signed zero/infinities/subnormals/NaN model); the verifier rejects it (`XAX.TYPE.FORM`), no float operation or execution semantics exist, and binary32-FTZ and E4M3FN stay structural in every catalog.

| Measurement | Result |
|---|---|
| Integer corpus (5 committed stores, 5 AI-task stores, 2 OI-03 workloads, 2 verified+executed reverse kernels; 26,703 B) | `bits5` −4,991 B (−18.7%); `common` −5,623 B (−21.1%); float entries change nothing |
| Per store | −6.1% (M14, opaque-heavy) to −29.1% under `bits5`; M14 −37.4% under `common` |
| Float reverse kernels (IEEE mix / with FTZ+E4M3FN; unverified) | `bits5` +1.8%/+1.7% (digest + 1 B/object, no hits); `float2` −15.5%/−11.5%; `float4` −24.6%/−11.5% |
| Descriptor size | `bits<N>` body 2 B, envelope 39 B; float body 7–9 B, envelope 44–46 B |
| AI spelling (o200k tokens) | `bits<N>` 4, `uN` 2, catalog `Tn` 2, CID hex 35–41; float structural 26–28, named (`binary32`) 2–3, catalog 2 |
| Store-wide CID dictionary comparator | Integer corpus −4,174 B (−15.6%); 34 dictionary entries cover 175 repeated references. It beats `bits5` on reference-heavy OI-03 stores but trails it on the integer corpus overall. |
| Codec complexity | Catalog alias 57 source lines; CID dictionary 97 source lines (encode + decode + container); no verifier change |

Findings. (1) Most byte savings are generic CID-reference compression rather than compact type descriptors. The store-wide dictionary shrinks the same 26,703 B integer corpus by 15.6%, versus 18.7% for `bits5` and 21.1% for `common`; thus `bits5` has an 817 B / 3.1 percentage-point advantage over a carried generic dictionary, while `common` has a 1,449 B / 5.5-point advantage. That incremental gain comes from the externally fixed vocabulary and omitted catalog objects, not a smaller structural type identity. (2) The generic dictionary wins where non-type references dominate: OI-03 mutual recursion is −1,333 B versus −1,119 B for `bits5`, and OI-03 non-recursive is −942 B versus −820 B. (3) A catalog must be a transport/store alias that expands to the structural descriptor: a canonical pre-interned body form is a second CID for the same type (test `test_catalog_body_form_would_split_identity`), violating canonical identity. (4) In AI-facing text a deterministic short name (`u32`, `binary32`) is as cheap as a catalog index; structural float text costs ~10x more tokens. (5) Catalogs with no hits cost the 32-byte digest plus one byte per object; the store-wide dictionary instead pays 32 bytes for each repeated CID it chooses to index.

**Extended evidence (2026-10-02).** The benchmark now uses the compiler's exact canonical binary32/binary64 type objects and adds a representative generated numeric corpus. `numeric_service_verified` is 6,231 B / 45 objects and uses binary32/binary64 in function signatures, CallContracts, pointer permission/address-space forms, vector-shaped arrays, and real stack load/store graphs; it passes the current verifier. `numeric_abi_extended` is 11,762 B / 86 objects and adds actual function/CallContract uses of exact measurement-only binary16/bfloat16 descriptors plus `vec<N,T>` descriptors, which remain unsupported by production semantics and therefore are not presented as verified language features. Across those two stores (17,993 canonical bytes), `bits5` is +197 B, `bits5_float2` is -1,250 B, `bits5_float4` is -1,720 B, and `common` is -2,270 B, while the carried generic repeated-CID dictionary is -2,901 B. Thus the fixed catalog does not beat generic compression on representative storage. The zero-hit float control is 1,629 B canonical and every fixed catalog is +45 B while the dictionary is -170 B; zero-hit entries are reported explicitly and the catalog still pays its 32-byte digest/container overhead. The extended corpus hits binary16/bfloat16 5 references each and binary32/binary64 12/10. Catalog codec complexity is 88 source lines versus 97 for the generic dictionary. The catalog decoder now validates the catalog digest, whole-container digest, record order, and exact index table instead of ignoring trailer/index corruption.

Eight deterministic AI mutation cells now cover bit width, binary32->binary64, binary16->bfloat16, vector lane count, pointer permission, pointer address space, vector creation, and one invalid-pointer repair. Structural-diagnostic and compact-alias arms have the same exact target CIDs and strict packet checkers. No external model or tokenizer trial was available in the execution environment, so `oi04_type_mutation_trials.json` records zero trials and the evidence JSON leaves model/tokenizer token fields unavailable rather than substituting bytes or historical offline counts.

**Still open.** The representative storage evidence favors generic CID compression over every fixed catalog tested, so no fixed transport/pre-interned vocabulary is justified by storage alone. The closure gate additionally requires actual model mutation reliability/token evidence; that evidence is unavailable. No catalog or CID-dictionary container is canonical, canonical type identity remains structural, and store v1 is unchanged.

## OI-05 — Proof-fact persistence

**Question.** Which derived facts should be serialized/persisted, cached separately, or recomputed?

**Fixed constraints.** Derived facts are never semantic authority and are invalidated with all meaning-affecting dependencies.

**Evidence that closes it.** Incremental verification/compile time, artifact/cache size, dependency maintenance cost, and cold/warm build measurements.

**Status: CLOSED (2026-10-01).** Successful object-verification facts are now a separate non-semantic `xax-proof-cache-v1` sidecar candidate, never semantic store records or semantic authority. Each entry is keyed by exact verifier identity, subject CID, and the subject's exact sorted direct-reference CID tuple. Only successful verification is cached. Whole-store digest/CID decoding and rooted/acyclic closure checks remain active; stale subject/dependency/verifier keys miss deterministically. Cache framing is canonical binary with its own BLAKE3 integrity digest; malformed/corrupt sidecars fail explicitly. `Workspace.load/save` can opt into a separate cache path, and successful local commits replace only the verified new frontier entries while pruning subjects no longer present. Deleting the sidecar leaves canonical store bytes, root identity, diagnostics, and compilation semantics unchanged.

Deterministic raw evidence is committed in `compiler/benchmarks/oi05_proof_cache_evidence.json` and reproduced by `bench_oi05_proof_cache.py`; the focused correctness suite is `tests/test_oi05_proof_cache.py`. The fixed workload contains 96 constant-return functions, 291 program objects / 42,155 store bytes, and a 296-object package-build snapshot / 42,935 store bytes; seven raw timing samples are retained for every timing arm. On this host, median verifier-only time falls from 92.65 ms cold to 42.46 ms warm (-54.2%). Including store/cache decoding across a restart, cold load+verify is 135.98 ms versus 124.27 ms with the persisted sidecar (-8.6%). Compiler-only time falls from 127.55 ms to 79.36 ms (-37.8%); restart-inclusive load+compile is 171.70 ms versus 162.73 ms (-5.2%). Build-only time falls from 218.56 ms to 171.81 ms (-21.4%), and restart-inclusive load+build from 319.64 ms to 253.19 ms (-20.8%). Generated artifact bytes/digests and provenance are identical in every cached/uncached arm.

The program proof cache is 33,639 B for the 42,155 B store (79.8%); the build-snapshot cache is 34,123 B for the 42,935 B store (79.5%). A one-function literal edit verifies/touches 5 objects and reuses 286. Cache maintenance invalidates exactly 5 old entries, writes exactly 5 new entries, accounts 102 direct dependency CIDs, keeps the cache at 291 entries / 33,639 B, and makes the immediately following compile 81.68 ms versus 127.61 ms without cache (-36.0%). The local commit itself is 397.86 ms with cache maintenance versus 388.34 ms without (+2.5%), so persistence is not free.

**Decision.** Proof facts MUST NOT be serialized into canonical semantic objects or treated as source. Successful verifier facts MAY be retained in a separate exact-key cache. In-memory reuse is the default economical reuse path; persistent sidecars are optional policy for workloads where repeated verification/build startup amortizes roughly 0.8x-store cache size and maintenance. Missing/stale cache entries recompute; corrupt sidecars may be discarded/recomputed or explicitly rejected. Any future proof-fact class with dependencies broader than `(verifier, subject CID, direct-reference CIDs)` must extend its cache key before reuse. Host timing magnitudes are evidence for this prototype policy, not normative performance thresholds.

## OI-06 — Alias/provenance representation and checked-access kernel surface

**Question.** What compact encoding should represent alias classes/provenance, and which checked memory operations deserve kernel status versus library specialization?

**Fixed constraints.** Ordinary accesses require proof; checked and raw behavior are explicit; provenance/permission cannot be fabricated.

**Evidence that closes it.** Verifier complexity, graph/token size, lowering/code-size quality, and target coverage on at least two materially different memory models.

**Status: CLOSED (2026-10-01).** The bounded memory-proof prototype now carries an explicit verifier-only alias-class fact derived from exact allocation-node provenance. Two simultaneously live allocations therefore form two precise independent provenance/alias classes without serializing any additional class identifier; `addr.offset` preserves that class. Cross-class pointer/effect use rejects deterministically. A comparator in `compiler/benchmarks/bench_oi06_memory_surface.py` shows that serializing local class IDs would add 2 graph bytes / 2 token-native semantic atoms to the two-allocation fixture while the allocation-derived representation adds zero. Explicit small class IDs remain reserved for conservative `may-alias` raw/target mappings where no precise storage-object identity is available; they are not emitted redundantly for ordinary object-backed pointers.

The same experiment adds measurement-only checked scalar load/store candidates with a dynamic `bits<32>` byte offset and explicit trap-on-failed-bounds behavior, plus a raw-load candidate. Ordinary and checked accesses still require live provenance and permission. Checked loads additionally require the entire candidate view initialized in this bounded prototype; checked stores do not fabricate initialization for an unknown dynamic offset. Raw load never fabricates provenance/permission or waives bounds: it requires `effect<unsafe>` and a nonzero explicit waiver mask and can currently waive alignment and/or initialization only. Canonical x86-64 and WebAssembly target package CIDs are unchanged; separate OI-06 target packages advertise these measured candidates.

Deterministic evidence is committed in `compiler/benchmarks/oi06_memory_surface_evidence.json` and reproduced by `compiler/tests/test_oi06_memory_surface.py`. `token_atoms` is the architecture's ideal token-native semantic-atom count (operations/value/type/attribute handles), not a third-party text tokenizer. On the fixed fixtures, checked load is +3 graph-body bytes / +4 store bytes / +1 token atom versus ordinary load, and checked store is +3 graph-body bytes / +3 store bytes / +1 token atom versus ordinary store. Raw initialized load is +6 graph-body bytes / +7 store bytes / +3 token atoms versus ordinary initialized load because the waiver and `effect<unsafe>` continuation remain explicit. Median cold verifier measurements over 31 samples were 3.19 ms ordinary-load versus 3.12 ms checked-load (-2.1%), 2.65 ms ordinary-store versus 2.87 ms checked-store (+8.1%), and 3.27 ms ordinary initialized-load versus 3.32 ms raw-load (+1.7%); the small/noisy deltas show that the added proof paths did not introduce a different verifier-complexity regime. These host timings are evidence, not normative thresholds.

Lowering preserves the semantic distinction on two materially different memory models. The OI-06 x86-64 package lowers the checked dynamic offset to a software unsigned bounds branch plus indexed frame-relative access; checked load/store each add 24 code bytes versus their ordinary static fixture. The OI-06 WebAssembly package lowers the same semantics to an explicit allocation-view bounds branch plus 32-bit linear-memory access; checked load/store each add 12 module bytes. The checked-load WebAssembly fixture executes offsets 0 and 4 and returns the two initialized words respectively. Raw load adds **0** emitted bytes on both targets relative to initialized ordinary load because its waiver/unsafe facts erase after verification.

**Decision.** Precise object-backed provenance is represented by storage-object/allocation identity and verifier-derived range/permission/alias facts; no second serialized local alias-class ID is carried. Conservative mappings MAY carry an explicit compact class ID only when exact object identity is unavailable. Dynamic scalar checked load/store deserve kernel status because their failure behavior is semantic, compact (+1 token-native atom in these fixtures), and lowers directly on both frame-relative native memory and WebAssembly linear memory. Statically proven accesses remain ordinary load/store and need no checked wrapper; higher-level slicing/indexing libraries should specialize to those ordinary forms when they can discharge the proof. Raw access remains a distinct explicit waiver form with an unsafe effect; the bounded prototype intentionally does not provide a general provenance-forging cast, borrow checker, ownership language, or bounds-waiving raw pointer primitive.

## OI-07 — DMA resource-state vocabulary

**Question.** Which common DMA ownership/mapping/cache states should be standardized across targets?

**Fixed constraints.** DMA ownership, mapping, cache maintenance, and synchronization are explicit when required.

**Evidence that closes it.** At least two substantially different target/platform packages with working DMA flows showing a stable shared vocabulary.

**Status: CLOSED (2026-10-01).** The bounded OI-07 experiment standardizes six semantic DMA-buffer states on the existing `resource<K,state>` mechanism: `host_unmapped`, `host_mapped`, `host_dirty`, `device_owned`, `device_pending`, and `host_stale`. The prototype encodes them as the compact state integers 1–6 under one experimental DMA resource kind; no new object kind, borrow/ownership language, device framework, or hidden runtime was added. `device_pending` is deliberately distinct from transferable `device_owned`, so a device write must pass through an explicit synchronizing operation before host ownership can be reacquired. `host_dirty` and `host_stale` similarly make required non-coherent clean/invalidate steps verifier-visible.

Deterministic evidence is committed in `compiler/benchmarks/oi07_dma_evidence.json` and reproduced by `bench_oi07_dma.py`; focused tests are in `tests/test_oi07_dma.py`. The first package, `oi07-noncoherent-split-dma-v1`, exposes separate host-only and device-only memory spaces and uses all six states in the explicit sequence acquire → map → host write → cache clean → device acquire → device write → synchronize → host acquire → cache invalidate → host read → unmap → release. The second package, `oi07-coherent-shared-dma-v1`, exposes one host/device-visible coherent space and uses the same shared vocabulary but legitimately omits the dirty/stale cache states and clean/invalidate operations: acquire → map → host write → device acquire → device write → synchronize → host acquire → host read → unmap → release. Both target packages verify, compile deterministically to the existing packet carrier (163 B non-coherent; 148 B coherent), and execute 4/4 fixed vectors with identical wrapping-add results.

Required operations are enforced by semantic state, not harness convention. Omitting cache clean from the non-coherent flow makes `host_dirty` fail the target contract expecting `host_mapped`; omitting synchronize on either target makes `device_pending` fail the host-acquire contract expecting `device_owned`. All three negative cases reject deterministically with `TARGET-OPERATION-TYPE`. The pre-existing M13 accelerator target CID remains unchanged.

**Decision.** The cross-target DMA-buffer vocabulary is the six states above. A package need only use states that its memory/coherence model requires: coherent targets may keep host writes/returns in `host_mapped`, while non-coherent targets use `host_dirty`/`host_stale` around explicit maintenance. Mapping/unmapping, ownership transfer, cache maintenance, device work, synchronization, and release remain explicit operations/effect transitions. Target/platform packages still define address spaces, legal transitions, scope, cache-operation necessity, and lowering; the shared vocabulary does not imply a universal DMA API or runtime.

## OI-08 — Effect partition granularity and persistent edge encoding

**Question.** How finely should memory/filesystem/network/device effects be partitioned, and should persistent stores encode explicit frontiers, compressed chains, or deterministic reconstruction?

**Fixed constraints.** The exact effect partial order is preserved; unproven independence is conservative; serialization order is never semantics.

**Evidence that closes it.** Optimization freedom, graph size, token cost, verifier time, and reconstruction cost on representative programs.

**Status: CLOSED (2026-10-01).** `compiler/benchmarks/bench_oi08_effect_edges.py` adds a benchmark-only comparison over the existing `effect<domain,instance>` model. It does not change the canonical graph/store schema. The corpus contains paired independent instances for each of `memory`, `filesystem`, `network`, and `device`, a 36-event four-domain workload with multi-domain steps, and a filesystem branch/merge case with two unordered roots and one two-predecessor join. Every XAX fixture is verified through the existing verifier before measurement. The candidate encodings are then checked against the exact authoritative footprint/frontier relation; both must reconstruct an identical transitive partial order before size or timing results are accepted.

Partition evidence selects **verifier-proven semantic instance** as the granularity rule rather than a fixed finer subdomain vocabulary. On each 8-event two-instance domain workload, refinement exposes 16 additional unordered effectful-operation pairs and cuts the effect critical path from 8 events to 4 for only +4 canonical graph-body bytes and +2 ideal token-native graph atoms. On the 36-event mixed workload, refinement exposes 162 additional unordered pairs and shortens the critical path from 13 to 6 for +16 graph-body bytes and +8 graph atoms. Median whole-store verification rises from roughly 2.8–3.2 ms coarse to 3.5–3.7 ms refined on the 8-event cases and from 7.99 ms to 10.50 ms on the mixed fixture on this host. These timings are observations, not thresholds. When independence is not proven, instance `0` remains the conservative shared frontier.

The persistent comparator measures (1) an **explicit frontier** section that repeats domain-instance handles and predecessor handles per event, and (2) **domain-grouped deterministic reconstruction**. The reconstruction arm carries explicit operation handles, groups them by domain instance in a semantic topological run, uses a compact “previous member” code for the common single-chain predecessor, and stores explicit backward predecessor deltas at roots/forks/joins. That run order is itself effect-semantic data; ordinary XAX node, record, CID, file, construction, or traversal order is never consulted. On each refined 8-event pair the effect section falls from 48 B / 44 token-native scalar-handle atoms to 36 B / 32 atoms (-25.0% / -27.3%). The 36-event mixed workload falls from 230 B / 226 atoms to 162 B / 158 atoms (-29.6% / -30.1%). The branch/merge case falls from 22 B / 18 atoms to 20 B / 16 atoms while preserving two roots and the exact two-predecessor join. Median candidate verification is also lower in these fixtures (mixed: 451.9 us explicit versus 349.2 us reconstructed), while mixed reconstruction alone costs 254.7 us; the small branch case reconstructs in 34.1 us. Raw timing samples and deterministic size/order results are committed in `compiler/benchmarks/oi08_effect_edges_evidence.json`; focused reproduction/rejection tests are in `compiler/tests/test_oi08_effect_edges.py`.

**Decision.** Memory/filesystem/network/device effects use the narrowest **proven** domain instance already expressible as `effect<domain,instance>`; XAX does not standardize a deeper universal file/socket/device/memory partition taxonomy. Unproven independence uses one conservative instance. For a future persistent effect-edge section, domain-grouped semantic runs with explicit fork/join predecessor deltas are preferred over repeating full explicit frontiers, because they preserve the identical partial order while reducing bytes/tokens and did not increase verifier cost on the measured corpus. The explicit frontier remains a valid verifier/internal normal form and fallback. OI-08 does **not** make either benchmark carrier part of canonical store v1; adopting the selected compression in a future schema still requires the ordinary schema-version process, but the representation choice itself is resolved.

## OI-09 — Indirect CallContract representation

**Question.** Should indirect-call effects/resources/capabilities/control be embedded with callable values, referenced through contract objects, or represented through sealed dispatch sets?

**Fixed constraints.** Every indirect call has a bounded verified contract; unbounded unspecified effects are invalid.

**Evidence that closes it.** Call-heavy workloads measuring object/token size, verifier cost, devirtualization, reuse, and package-interface stability.

**Status: CLOSED (2026-10-01).** `compiler/benchmarks/bench_oi09_call_contracts.py` builds five verified direct-call contract families (pure value, filesystem effect, network effect, device effect plus an explicit resource-typed authority value, and non-returning trap control), 15 exact dispatch sets, and two 960-indirect-call placement profiles. The comparator uses the same exact direct-function interface/effect/control facts for all three arms: (1) contract fields embedded in every callable carrier, (2) separately content-addressed referenced CallContract objects, and (3) sealed exact-target sets carrying the bounded union contract. Every candidate is rejected unless every callable resolves a finite bound and every admitted target stays within it; there is no unknown-effects arm. Raw deterministic corpus identities, placement sizes, reuse/devirtualization facts, package-edit churn, and host timing observations are committed in `compiler/benchmarks/oi09_call_contract_evidence.json`.

In the **reuse-heavy** profile (120 callable values, 960 calls), embedded/referenced/sealed metadata measures **9,962 / 9,737 / 11,651 bytes** and **1,801 / 1,231 / 1,341 ideal semantic atoms**. Median placement verification on this host is approximately **2.51 / 0.60 / 0.77 ms**. Referenced contracts therefore save 2.3% bytes and 31.6% atoms versus embedding while verifying about 76% faster. Each of the five referenced contract objects is reused by 24 callable values.

The **sparse-callable** profile deliberately keeps the same 960 calls but uses only 15 callable values (three per contract). It records the crossover instead of hiding it: embedding is smaller (**2,087 B**) than referencing (**2,387 B**), while referenced contracts still use fewer semantic atoms (**1,021 vs 1,066**) and verify faster (approximately **0.29 vs 0.36 ms**). Sealed sets remain largest (**4,301 B / 1,131 atoms**) and slowest of the two reusable-object candidates in this profile. This shows that direct embedding can be a useful future serialization compression for low-reuse contracts, but it is not the best semantic authority placement.

Sealed sets uniquely expose exact-target optimization information: all sealed callables have exact sets and one third of calls are singleton-devirtualizable in both profiles. The cost is interface coupling. Replacing one implementation with a new function CID while preserving the exact same derived CallContract changes **3 sealed-set identities** and forces **192 indirect-call references** through affected callable carriers to rebind (24 carriers in the reuse-heavy profile; 3 in the sparse profile). The separately referenced CallContract CID is unchanged, and embedded contract bytes are likewise unchanged but have no independent reusable identity.

**Decision.** The semantic representation is a separately content-addressed **referenced CallContract object**. Callable values reference that bounded contract identity. Exact sealed dispatch sets are optional additional optimization facts for devirtualization; they do not replace the contract and cannot create an unspecified-effects escape hatch. Full contract embedding is not semantic authority, though a later persistent serializer may deterministically compress low-reuse references if it reconstructs the identical contract identity. Prototype kind 11 implements the smallest winning reusable object: exact input/output type references plus return/trap bounds; current effect bounds and resource/capability-bearing value requirements are reconstructed from the exact typed interface. The compiler still has no general indirect-call opcode, so this closes the **representation** issue without claiming indirect-call execution/lowering support.

Focused OI-09 tests cover deterministic identity, exact direct-function bounding, noncanonical-control rejection, rejection of an effectful function under an empty contract, all three placement comparators, sealed cross-contract target rejection, the measured byte crossover, and committed-evidence reproduction.

## OI-11 — Non-native atomic synthesis policy

**Question.** When should unsupported atomics become bounded inline sequences, explicitly permitted runtime assistance, or hard rejection?

**Evidence that closes it.** Correctness, code size, latency, lock-free/progress behavior, and target diversity across multiple architectures.

**Status: CLOSED (2026-10-02).** Exact target capability remains authoritative. `native` is selected only for an exact supported address-space/width/alignment/family/order/scope request. `bounded_sequence` is selected only when the target/backend has a finite declared inline sequence, finite retry behavior, an exact maximum sequence instruction count, and `permit_bounded_inline=true`; otherwise the request rejects. `runtime_assist` requires explicit policy permission plus an explicit helper identity and backend-declared helper contract; no current target implements one, so absent/undeclared assistance rejects rather than synthesizing a helper. ## OI-37 — Pointer values stored in memory

**Question.** How should pointer-typed values be stored to and loaded from memory (provenance, extent, permission, alias class, target pointer width) so that iovecs, linked structures, vtables, and object graphs are expressible without raw waivers?

**Fixed constraints.** Provenance is never manufactured: a loaded pointer carries at most the facts the verifier can re-establish; unknown provenance stays explicit (checked/raw policy). Pointer width/layout comes from the target ABI, not the kernel. No hidden runtime metadata.

**Evidence that closes it.** One representation that admits WASI `fd_write` iovecs and a heap linked list with verified traversal on two targets of different pointer widths, plus negative vectors for forged/expired provenance, with measured verifier cost and AI tokens per edit.

**Status: CLOSED (2026-10-02, ADR-096).** Closure evidence, criterion by criterion:

- *WASI `fd_write` iovecs:* address-valued interface structs via `pointer_address` (ADR-081), executed under `node:wasi`.
- *A linked list with verified traversal on two pointer widths:* x86-64 Linux, 64-bit, heap views (`chains` with `pointer_rebase`, 2^20 nodes, ADR-092); wasm32, 32-bit (`test_xax_wasm_rebase.py`, ADR-093). Deviation stated: the wasm32 list lives in stack storage, because the wasm32 profile has no heap allocator; the representation and the checks are identical.
- *Negative vectors:* forged, misaligned, below-view, and wrapped addresses trap on both targets. Expired provenance (rebase after unmap or `stack_end`) rejects with `MEMORY-LIFETIME-LIVE` on both targets, and authority, extent, alignment, width, and initialization violations reject on x86-64.
- *Verifier cost* (`oi37_closure_evidence.json`): `verify_store` costs 47.9 µs per additional rebase+load against 46.8 µs per checked load (straight-line, K = 1–256). Pointer-linked `chains` verifies in 2.7 ms, index-linked in 2.6 ms.
- *AI tokens per edit* (offline tiktoken 0.14.0, no model run): switching `chains` from index to pointer links rewrites 4 objects (4,458 envelope bytes, 4,198 `o200k` hex-carrier tokens). The operation delta is 11 operations, 87 `o200k` tokens in a compact `[±, operation, attributes, count]` view.

Check-free reloads, which remove the per-link check (1.5× in C on `chains`), are not part of the closure criteria and move to OI-41.

**History.** OPEN (partially addressed). ADR-081 adds one-way provenance exposure (`pointer_address`), which unblocks address-valued interface structs (WASI `fd_write` iovecs, executed). ADR-082 admits provenance-free pointers (function addresses, external pointers) as memory elements, unblocking function-pointer/dispatch tables (EXECUTED on Windows PE). Still open: storing pointers *with* local provenance and reloading them as dereferenceable pointers (pointer-linked lists/trees over XAX storage), which needs typed mixed storage and lifetime coupling between the container and the referenced storage; arena + index is the current verified alternative. Memory elements remain whole-byte bits/float scalars (`MEMORY-BYTE-ADDRESSABLE-VALUE`).

**Progress (2026-10-02, ADR-092).** `pointer_rebase` (op 73) reloads an exposed address as a pointer inside a live view, with one range+alignment check, so field reads need no further checks. Pointer-linked `chains` measures 1.64× `gcc -O2` and 1.07× C with the same check; index links measure 2.00×. wasm32 (32-bit pointers) executes the same representation with trap vectors (ADR-093). Remaining for closure: check-free reloads (typed storage) and AI tokens per edit, with verifier cost.

**Measured justification (2026-10-02, ADR-090).** On a 2^20-node chained hash table (`oi37_chains_evidence.json`), arena + index links cost 1.44–1.47× versus pointer links in C, and the bounds checks equivalent to XAX's checked access cost a further 1.34–1.41×. The ADR-082 falsification condition is met for speed. A design that closes this must carry node extent with the provenance, so the per-access check disappears along with the index scaling. Sequenced after OI-38, whose measured share (1.73–1.80×) is larger.
